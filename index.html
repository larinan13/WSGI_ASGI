WSGI ⇄ ASGI

⚡ Мост между сервером и Python-кодом PEP 3333 → ASGI #async
📜

WSGI · PEP 3333 синхронный

Web Server Gateway Interface — стандарт, объединивший серверы и фреймворки.

  • Проблема: До WSGI каждый фреймворк (Django, Flask) был жёстко привязан к конкретному серверу (CGI, mod_python).
  • Решение: WSGI ввела универсальный контракт: application(environ, start_response).
  • Синхронная модель: один запрос → один поток/процесс.
  • До сих пор используется в Flask, Django (по умолчанию).
⚡

ASGI · Async асинхронный

Asynchronous Server Gateway Interface — эволюция WSGI.

  • Почему WSGI не подошла: блокировка потоков, нет WebSocket, сложное масштабирование.
  • Решение: ASGI ввела асинхронный event-loop и интерфейс async def app(scope, receive, send).
  • Поддерживает WebSocket, HTTP/2, SSE, долгие соединения.
  • Используется в FastAPI, Starlette, Django + Channels.

⚠️ Почему WSGI уступила место ASGI?

Блокировка

Поток занят до конца обработки — плохо для I/O (БД, API).

Нет WebSocket

Только HTTP запрос-ответ, без долгих соединений.

Масштабирование

Требует много процессов/потоков → дорого по памяти.

🧩 Серверы приложений — их роль

🐍 Gunicorn (WSGI)
⚡ Uvicorn (ASGI)
🐝 Daphne (ASGI)
🌽 Hypercorn (ASGI)

Их задача: принимать запросы от веб-сервера (Nginx/Apache), преобразовывать их в вызовы Python-функций по стандарту WSGI/ASGI и возвращать ответ.

  • Gunicorn — классический WSGI-сервер, запускает несколько рабочих процессов (pre-fork).
  • Uvicorn / Daphne / Hypercorn — ASGI-серверы, используют цикл событий asyncio для обработки тысяч соединений.

📋 Детальный разбор жизненного цикла HTTP-запроса

Шаг 1

🌐 Браузер отправляет запрос

Пользователь вводит URL или кликает по ссылке. Браузер формирует HTTP-запрос (GET /api/users HTTP/1.1) и отправляет его на сервер.

Шаг 2

🔄 Веб-сервер (Nginx/Apache) принимает

Nginx принимает соединение, обрабатывает статику (CSS/JS/картинки) и проксирует динамические запросы к серверу приложений через WSGI или ASGI.

Шаг 3

🐍 Сервер приложений (Gunicorn/Uvicorn)

Сервер приложений преобразует HTTP-запрос в вызов Python-функции:

• WSGI: application(environ, start_response)
• ASGI: await app(scope, receive, send)

Шаг 4

🧩 Python-фреймворк (Flask/Django/FastAPI)

Фреймворк обрабатывает запрос: парсит URL, вызывает нужный контроллер, работает с БД, формирует ответ (JSON/HTML).

Шаг 5

⬆️ Формирование HTTP-ответа

Фреймворк возвращает ответ (статус, заголовки, тело). Сервер приложений упаковывает его в HTTP-формат.

Шаг 6

🔙 Обратный путь через Nginx

Ответ проходит обратно через Nginx (может добавить сжатие, кеширование) и отправляется браузеру.

Шаг 7

🌐 Браузер отображает ответ

Браузер получает HTML/JSON, рендерит страницу или обрабатывает данные через JavaScript.

⚡ Особенность ASGI

WebSocket / долгие соединения

В ASGI соединение не закрывается после ответа — оно остаётся открытым для двусторонней коммуникации (чаты, уведомления, игры).

🔄 Визуальная схема жизненного цикла

💡
Ключевой вывод: WSGI и ASGI — это стандарты интерфейсов, а не серверы. Они позволяют отделить логику приложения от инфраструктуры. ASGI — естественное развитие для современных высоконагруженных и интерактивных приложений, работающих с WebSocket и асинхронным I/O.

Выбор: для классических монолитов — WSGI (Flask, Django), для современных API и реального времени — ASGI (FastAPI, Django + Channels).
